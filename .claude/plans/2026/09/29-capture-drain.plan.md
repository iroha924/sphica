# capture の送信を、送信待ちが空になるか持ち時間が尽きるまで続け、保留分が新しい記録を塞がないようにする（W8、#188）

## 要点

- `flush()` は 1 回で 500 件までしか送らず、未登録リポジトリの保留分（`spool/unregistered/`）を送信待ちと一緒に古い順で選ぶ。700 件で 200 件が残る、保留 500 件で登録済みの新しい 1 件が送られない、の 2 つを再現した
- 送信待ち（`spool/`）を 500 件ずつ、空になるか持ち時間が尽きるまで繰り返し送る。保留分は 1 回の `flush()` につき 1 度だけ、最初に控えた一覧の分を見直す
- 持ち時間は呼び出し元で分ける。Stop と Interrupt の裏の送信は 30 秒、MCP ツールの中（`extract.ts`）は 2 秒。確かめるのはバッチの間だけ
- ロックを外した後に送信待ちを見直し、残っていれば取り直す。ロックが取れずに何もしなかった別の送信の分を取り残さない
- 変えないもの: 保留分の保持の規則（30 日・1000 件）、doctor の表示、DB と SQL の書き込み箇所

## 持ち主の決定

- 選別の順序で W2 の次に W8 を進める（2026-09-28）
- #188 の求める結果: まず一時 HOME で再現する。再現したら、送信待ちが空になるか時間の上限まで送り、保留分が送れるものを飢えさせない選び方にする（issue 本文）

## 目的

- 1 回の `flush()` で、始めた時点の送信待ち（と、送信中に積まれた分）が、持ち時間の内なら全部 DB に入る
- 登録済みプロジェクトの記録は、保留分が何件あっても送られる
- 送信中にロックが取れず何もしなかった送信があっても、その分が次のフックまで残らない

## 対象外

- 保留分の保持の規則（`prune` の 30 日・1000 件）の変更。見直す順序（送る前に prune する）だけ変える
- doctor と SessionStart の表示。`readState()` は保留件数を別に数えている（`server/src/capture.ts:449-465`、`server/src/cli.ts:145-153`）
- SQL の追加。`write()` と project の select を繰り返し呼ぶだけ

## 前提

- 再現（2026-09-29、一時 HOME と実 SQLite、`server/test/capture.test.ts` の末尾に追加した 2 件、未コミット）: 700 件で `sent: 500, left: 200`。保留 500 件と登録済みの新しい 1 件で `sent: 0`
- `flush()` は `spool/` と `spool/unregistered/` の一覧を合わせて名前（時刻が頭）で並べ、`BATCH = 500` で切る（`server/src/capture.ts:651-674`）。登録されないままの保留分は動かず消えないので、毎回先頭に来る。`prune` は 30 日か 1000 件を超えた分だけ消す（`capture.ts:46-47, 153-167`）
- 呼び出し元: Stop と Interrupt のフックが裏で `capture --flush` を 1 つ起動する（`capture.ts` の `main()`）。`server/src/extract.ts:39,86,94`（`pendingText`・`beginTrace`・`beginGlean`）は MCP ツールの中で `flush()` を待つ
- ロックは 5 分で古いとみなされる（`capture.ts` の `lock()`）。取れないと `busy` を返して何もしない
- 実測（2026-09-29、この Mac）: 2 KB の発言 500 件を一時 SQLite へ 1 回送ると 54 ms。混んでいるときの上限ではない。1 バッチは SQLite の busy 待ち（5 秒、`server/src/sqlite.ts:54-56`）と 1 件ずつの送り直しで延びうる
- `capture.ts` は `sql:reach` の `LIVE_FILES`（`scripts/lib/sql-call-sites.mjs:42`）。関数を直接呼ぶテストは数えられず、`sql:live` の子プロセスが通常・未登録・後から登録の送信を通している（`scripts/check-sql-live.mjs:53-109`）
- 同じ記録の再送は capture のビューのトリガーが受け流す（`db/schema.sql:692-725`）。spool のファイルは別名で書いて rename する（`capture.ts:169-176`）

## 方針

`server/src/capture.ts`:

- 定数を `BATCH` の隣に置く: `FLUSH_BUDGET_MS = 30_000`（裏の送信）、`TOOL_FLUSH_BUDGET_MS = 2_000`（MCP ツールの中）
- `flush(file = dbFile(), budgetMs = FLUSH_BUDGET_MS)`。締め切りは開始時刻 + `budgetMs`。確かめるのはバッチの間だけ（1 バッチは締め切りを越えうる、とコメントに書く）
- 1 バッチの処理（読む・project を引く・`write()`・rejected と保留への移動・送ったファイルの削除）は今の本体を関数に切り出して使い回す。SQL の呼び出し箇所は増やさない
- 流れ:
  1. ロックを取る。取れなければ `busy`（今と同じ）
  2. 最初のロック保持でだけ: `prune(held)` → 保留の一覧を控える → 控えた分を 500 件ずつ 1 度だけ処理する（登録済みになった分は送り、残りはそのまま）。今回の送信の途中で保留に回った分は控えに入らないので読み直さない
  3. `spool/`（`unregistered/` と `rejected/` を含まない）を古い順に 500 件ずつ、空になるか締め切りまで繰り返す。未登録の分は今どおり保留へ移す
  4. `prune(held)` し、保留の件数を数えて `deferred` とし、ロックを外す前に `writeState` する（後の送信が書いた失敗の状態を上書きしないため、ロック保持ごとに外す前に書く）
  5. ロックを外す。`spool/` に `.json` が残っていて締め切り前なら 1 に戻る（2 は飛ばす）。ロックが取れなければ、その持ち主が外した後に同じ見直しをするので終える
- 2 と 3 の順序: 保留の見直しを先にするのは、控えた一覧が有限で必ず終わるため。送信待ちを塞がないのは、保留分を送信待ちと同じ 500 件の枠で選ばないため
- 返り値: `sent` と `rejected` は全バッチの合計。`deferred` は最後の prune の後の保留件数
- 例外（接続断など、記録のせいでない失敗）は今どおり状態に書いて投げ直す。それまでのバッチはコミット済みのまま

`server/src/extract.ts`: 3 か所の `flush()` を `flush(undefined, TOOL_FLUSH_BUDGET_MS)` にする。

テスト（`server/test/capture.test.ts`、一時 HOME と実 SQLite）:

- 再現 2 件を回帰テストにする: 700 件 → 全部送り残り 0。保留 500 件 + 新しい 1 件 → `sent: 1`、保留は 500 件のまま
- 後から登録したプロジェクトの保留分が、保留の見直しで送られる
- 期限（30 日）を過ぎた保留分は、プロジェクトが登録済みでも送らずに消える
- 締め切り: `budgetMs = 0` で 1 バッチだけ送って止まる（実時間を待たない）
- 取り残し: `node:test` の `mock.method(fs, "readdirSync", ...)` で、ロック保持中に `spool/` の空の一覧を返す直前に 1 件積み、2 つ目の `flush()` を await して `busy` を確かめる。その後 1 つ目がその 1 件を送り `spool/` が空であることを確かめる。積むのは 1 度だけ、mock は finally で戻す

出荷: パッケージに入る変更なので `release:plan` の判定に従い、npm と 3 つの plugin manifest を同じバージョンに上げる。

## 採った案と棄却した案

- 採用: 送信待ちと保留分を分けて選び、送信待ちは締め切りまで繰り返す。棄却: `BATCH` を大きくする（上限も飢えも残る）
- 採用: 1 つのプロセスの中で繰り返す。棄却: `main()` から送信のプロセスを追加で起動する（プロセスが増え、飢えは残る）
- 採用: 保留分は最初に控えた一覧だけを 1 度見直す。棄却: 保留分を送信待ちの後ろに並べて同じ 500 件の枠で選ぶ（送信待ちが 500 件以上あると保留分が送られない）
- 採用: 持ち時間を呼び出し元で 30 秒と 2 秒に分ける。棄却: 共通の 20 秒（MCP ツールを長く待たせる根拠が無い）
- 採用: `writeState` はロック保持ごとに外す前に書く。棄却: 最後に 1 度だけ書く（後の送信の失敗の状態を成功で上書きしうる）
- 採用: 取り残しのテストは `fs.readdirSync` の mock で順序を固定する。棄却: `flush` にテスト専用の引数を足す / 並行の非同期タスクで起こす（順序が決まらず不安定）
